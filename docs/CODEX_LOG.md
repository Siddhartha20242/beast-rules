## Stability fix: contain Twitch/OBS network errors and reconnect (written with another AI assistant, not Codex)

- **Authorship note:** This one change was written by an AI assistant other than Codex (the planning assistant), at the owner's request. Everything above this entry was built by Codex in the thread described in the README.
- **Problem:** During live testing the server exited with code 1 after an EventSub WebSocket keepalive timeout. `ws` emitted an `error` event on a socket that was still connecting, and nothing listened for it, so Node terminated the process.
- **Library finding:** Twurple's persistent connection retries forever and `EventSubWsListener.stop()` followed by `start()` is safe because the subscription list is kept. The crash was only the unhandled error.
- **Produced:** `src/twitch/resilience.ts` (`isRecoverableNetworkError`, `handleProcessError`, `installProcessGuards`, `ReconnectSupervisor`); runtime wiring in `src/twitch/runtime.ts` (supervised first connection, restart on prolonged outage, connection status); `src/health.ts` and `src/server.ts` (`/health` fields `twitchReconnecting`, `lastDisconnectAt`, `reconnectAttempts`, a light `/api/twitch-status` endpoint, process guards, retry of a failed first start); a "Twitch reconnecting" dot in `public/overlay.html` (hidden with `?obs=1`) and a reconnecting label in `public/sandbox.html`; 14 new tests in `tests/resilience.test.ts`; one assertion updated in `tests/observability.test.ts` for the three new health fields.
- **Design decision:** The supervisor waits 5s, 10s, 20s then 30s between restarts instead of starting at 1s, because Twurple already retries within the first seconds and an earlier restart would fight its own reconnect.
- **Live check:** Froze the running server with SIGSTOP for 40 seconds to mimic a laptop sleeping, then resumed it. The process stayed up, logged "disconnected; reconnecting", reconnected, and `/health` showed `twitchConnected: true` with all 7 subscriptions active and `lastDisconnectAt` set. The exact stray `ws` error did not fire in this run (it is timing dependent), so the guard for it is covered by a unit test built from the real error's stack shape, not by the live run.
- **Checks:** `npm test` passed (210 tests across 16 files), `npm run build` passed, `npm run lint` passed.
- **Failures:** One existing test (`tests/observability.test.ts`) failed on first run because it compared the whole health response and the response gained three fields; its expectation was updated.

## Easier screen recording: dark backdrop URL and auto-start demo (written with another AI assistant, not Codex)

- **Why:** Recording the overlay in a normal browser tab needed a console command for a dark backdrop, and the demo needed Enter to be pressed during the recording.
- **Produced:** `?bg=dark` on the overlay URL paints a dark backdrop (OBS stays transparent without it). `npm run demo:auto` starts the demo by itself after 20 seconds (`DEMO_DELAY`); `npm run demo` still waits for Enter. The demo prints the `bg=dark` URL.
- **Checks:** `npm test` (268), `npm run build` and `npm run lint` pass; the computed page background was confirmed in a browser.

## Crisis recording scripts made to watch the server (written with another AI assistant, not Codex)

- **Why:** A first version of `npm run crisis` used fixed delays. On a server started without the short timers (30-second votes) it printed "Crisis open" and "Done" even though the new law had not yet passed and no crisis ever started.
- **Produced:** `scripts/crisis.ts` now polls `/api/state`. `crisis:setup` waits for the horns law to be in force; `crisis` refuses to run without a head law, waits for the crisis to open and for it to finish, and stops with a plain message if anything is missing. No application code changed.
- **Checks:** run live in four cases: crisis without setup (stops with a clear message), setup then crisis with short timers (new law wins, scar in the head zone), setup run twice (stops with a clear message), and setup then crisis with default timers (87 seconds, same result). `npm run lint` and `npm run build` pass.
